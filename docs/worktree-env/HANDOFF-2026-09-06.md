Everything a Claude session in another repo (bluecity-viz first) needs to
reproduce the resslab-hub worktree setup at the same quality. Written on
2026-09-06 from resslab-hub commit `4bb97e8` (branch `dev`).

Sources, in this order of authority:

1. `scripts/wt-*.sh`, `scripts/tmux-dev.sh`, `scripts/git-push-guard.sh`,
   `scripts/claude-worktree-settings.json`, `.wt.toml` in resslab-hub.
2. `docs/worktree-dev-environment.md` (the full guide, with the why).
3. `CLAUDE.md`, section "Dev servers and worktrees" (the rules the agent reads).
4. This file: the short version, the lifecycle end to end, what changed since

`git -C ~/code/resslab-hub show dev:scripts/wt-setup.sh` (and so on), or copy
the files. Do not work from memory of what the scripts do.

## 1. The idea

One branch = one git worktree = one tmux session = one Claude Code agent with
its own backend and frontend servers (and, in resslab-hub, its own database).
Nothing is shared between worktrees except the git object store.

```
wtgo feat/x                    (or: make new BRANCH=feat/x, or: wt create feat/x origin/dev)
  └─ scripts/wt-new.sh         fetches origin/dev, `wt create` (or `wt checkout` if the branch exists)
       └─ .wt.toml post_create → scripts/wt-setup.sh      (idempotent)
            ├─ 0. branch tracking: autoSetupMerge simple, upstream = origin/<branch> or none
            ├─ 1. seeds gitignored dev files from the main checkout (never overwrites)
            ├─ 2. hashes the branch name → .env.worktree (WT_BRANCH, WT_SLUG, BACKEND_PORT, FRONTEND_PORT, ...)
            ├─ 3. wires this frontend to this backend, this backend to its own DB
            ├─ 4. writes .claude/settings.local.json from the MAIN checkout's template
            ├─ 5. make install && make hooks (skipped when deps are already there)
            └─ 6. scripts/tmux-dev.sh --no-attach → tmux session "<repo>/<branch>"
       └─ attach (or switch-client when already inside tmux)
wtdone feat/x                  session killed, worktree removed, branch kept
  └─ wt remove → .wt.toml pre_remove → scripts/wt-teardown.sh   (kill session, free ports, drop branch DB)
make wt-land BRANCH=feat/x     from the main checkout: rebase, PR, squash-merge into dev, remove everything
```

Four invariants hold it together. Break one and worktrees cross-talk in ways
that look like application bugs.

- **`.env.worktree` is the single source of per-worktree values.** Nothing
  reads it directly. `tmux-dev.sh` exports it in every pane, and every tool
  (Makefiles, vite, pytest, the scripts) reads plain environment variables.
  The main checkout has no such file and keeps the classic ports.
- **Every port is a variable with the old value as default.** Backend port,
  vite port, vite proxy target, any `VITE_*_URL`, CORS origins, OAuth redirect
  URIs, test base URLs. `grep -rn "8000\|5173"` and fix every hit.
- **The frontend reaches the backend through the vite `/api` proxy**, on a
  relative URL, same-origin. Never an absolute backend URL in a dev env file:
  the browser would hit the backend port directly, and cookies and CSRF break.
- **A worktree owns exactly one branch.** It pushes that branch and nothing
  else, never the protected ones. Three layers enforce it (section 5).

## 2. The lifecycle, step by step

### 2.1 Create

`wtgo <branch> [base] [--prompt <file-or-text>] [--no-attach]` is a bash
function from `scripts/wt-go.bash` (tab completion), running
`scripts/wt-new.sh`. `make new BRANCH=... [BASE=...] [PROMPT=...]` and
`make go` do the same without completion.

- Refuses protected branches (`dev`, `stage`, `main`): a worktree holding the
  default branch becomes wt's "main" and breaks its path resolution.
- Base defaults to `origin/dev`, fetched first. A local ref is a stale base.
- A branch that already exists (local or origin) is adopted with
  `wt checkout`, the same hooks run.
- `wtgo all` (after a reboot) starts every set-up worktree's session detached,
  then opens the tmux session picker. Only worktrees with a `.env.worktree`
  count.
- Works from anywhere: it resolves the main checkout through
  `git rev-parse --git-common-dir`, never through `$WT_MAIN` (wt points that at
  whichever worktree has the default branch checked out).

`wt create` runs the `post_create` hook; some wt builds run `post_checkout` on
create too. Both point at `wt-setup.sh`, which is idempotent for that reason
and can be re-run by hand at any time to refresh a worktree.

### 2.2 Setup (`scripts/wt-setup.sh`)

Numbered as in the script. The generic steps are 0, 2, 4, 6. Steps 1, 3, 5 are
where a repo puts its own needs.

0. **Branch tracking.** `git config branch.autoSetupMerge simple` and
   `push.autoSetupRemote true` (repo-level, so every checkout gets them), then
   the worktree's branch is pointed at `origin/<branch>` if that exists,
   otherwise its upstream is removed. Without this, a branch cut from
   `origin/dev` tracks `dev`: `git pull` rebases it onto dev, the next push is
   refused, and one rebase left a HEAD detached (2026-09-06).
1. **Seed gitignored dev files** from the main checkout's disk copies, never
   overwriting: `secrets/.env`, `docker-compose.override.yml`,
   `frontend/.env.development.local`, the generated `sample-data/` batches.
   Big untracked data should be symlinked, not copied (bluecity-viz does this
   for its 100 MB of PMTiles).
2. **Ports and names.** `cksum` of the branch name, `BACKEND_PORT = 18000 + h % 500`,
   `FRONTEND_PORT = 19000 + h % 500`. Same remainder on both, so `18042 / 19042`
   read as one worktree and the same branch always gets the same pair. Written
   to `.env.worktree` together with `WT_BRANCH`, `WT_SLUG` (branch name made
   safe for identifiers) and the repo's extra keys (`DB_NAME`,
   `POSTGRES_TEST_DB`, `RESSLAB_DATA_DIR` in resslab-hub).
3. **Wire the app.** In resslab-hub: drop any absolute `VITE_APP_BACKEND_URL`
   from the dev env file (the vite proxy reads `BACKEND_PORT` itself), point
   `secrets/.env` at the branch database, migrations off on the shared DB, then
   clone the branch DB (`wt-db.sh create`). In a repo where vite reads the
   ports from the environment and there is no database, this step is empty.
4. **Claude settings.** `scripts/claude-worktree-settings.json` from the
   **main checkout** (not the branch: a branch forked before a template fix
   would write the old rules back, and a feature branch must not be able to
   change Claude's permissions) is rendered to the gitignored
   `.claude/settings.local.json`.
5. **Dependencies and hooks.** `make install` when `node_modules` / `.venv`
   are missing, then `make hooks` (lefthook refuses commits from a checkout
   where it is not installed). Disk: uv hard-links `.venv` from `~/.cache/uv`
   and pnpm hard-links `node_modules` from its store, so a resslab-hub
   worktree costs tens of MB. With npm each worktree carries its own ~500 MB.
6. **Session.** `scripts/tmux-dev.sh --no-attach`, with `ROOT` exported so the
   main checkout's copy of the script can serve a branch that predates it.

### 2.3 The session (`scripts/tmux-dev.sh`)

One session `<repo>/<branch>` (`.` and `:` mapped to `-`, tmux forbids them),
one window `dev`, four titled panes: `claude` fills the left half and has
focus; `backend`, `frontend` and `shell` stack on the right. Also
`make tmux-dev-all` in any checkout (the main one included, on 8000/5173).
`make dev-all` is the plain version: both servers in the current terminal.

- Every pane starts with the `LOAD` prefix: export `.env.worktree` if the
  checkout has one, else **unset** those keys (`ENV_WORKTREE_KEYS`). The unset
  matters: a tmux server started from a shell that had a worktree's file
  sourced would hand its ports to every later session, including the main
  checkout's. The script also scrubs `ROOT` and those keys from the server
  environment on every run.
- `backend` and `frontend` panes run `make dev` in their directory, and mirror
  their output to `.wt-logs/backend.log` / `.wt-logs/frontend.log` with
  `tmux pipe-pane`. The agent's sandbox cannot reach the tmux socket, so these
  files are its only view of the servers.
- `claude` pane: with a `PROMPT.md` at the checkout root it runs
  `mv PROMPT.md PROMPT.sent.md && claude --model fable --permission-mode plan "$(cat PROMPT.sent.md)"`
  (`WT_BRIEF_MODEL` / `WT_BRIEF_PERMISSION_MODE` override, empty keeps
  claude's defaults). Otherwise `claude --continue || claude`: resume the
  checkout's last conversation, or start fresh on a new worktree. The pane
  carries a `@wt_role=claude` option, because claude rewrites the pane title.
- The database container is started from the **main checkout** when missing
  (compose names its project after the directory; a worktree would create a
  second project fighting for the port).
- Server options refreshed on every run: `detach-on-destroy off` (killing a
  session hops the client to another one instead of leaving tmux), and
  `prefix+X`, a menu on the current session: kill, "done" (wt-done.sh on the
  pane's checkout), or a confirmed force variant that discards uncommitted
  changes.
- Prints the URLs (`http://localhost:$FRONTEND_PORT/`,
  `http://127.0.0.1:$BACKEND_PORT/docs`) and attaches, or `switch-client`
  when already inside tmux.

### 2.4 Briefing an agent (`--prompt`)

`wtgo feat/x --prompt brief.md` (a readable file is copied; anything else is
taken as literal text, but a value that looks like a path and is not a file
is an error) writes `PROMPT.md` at the worktree root and passes `--brief` to
`tmux-dev.sh`. Because the `post_create` hook has already started the session
by then, `--brief` restarts the `claude` pane on the brief (`respawn-pane`).
The previous conversation stays resumable with `claude --continue`, but never
brief a worktree whose agent is mid-task.

Rename to `PROMPT.sent.md` happens before the run, so a session recreated
later (`wtgo all`) resumes instead of firing the brief twice. `PROMPT.md`,
`PROMPT.sent.md` and `.wt-prompts/` (drafts) are gitignored.

Chain several from one shell, one per line, never with `&`
(`git worktree add` races on its locks):

```bash
wtgo feat/a --no-attach --prompt .wt-prompts/a.md
wtgo feat/b --no-attach --prompt .wt-prompts/b.md
wtgo all
```

This is how multi-stream work is delegated: one worktree per stream, each
agent starts in plan mode on its brief and comes back with a plan to review.

### 2.5 Finish

Three ways, from the least to the most final.

- **`wtdone <branch>`** (`scripts/wt-done.sh`, also `make wt-done` and the
  `prefix+X` menu): kill the session, `wt remove` the worktree (fires the
  teardown hook), keep the branch local and remote. Refuses a dirty worktree
  unless `--force`. Unpushed commits stay on the local branch and the script
  says so. Run from inside the very session being closed, it hands itself to
  the tmux server (`run-shell -b`) so the kill does not take it down, and it
  always re-executes the **main checkout's** copy of itself: bash reads a
  script while running it, and the worktree copy disappears mid-run.
- **`make wt-land BRANCH=<branch> [MODE=--local]`** (`scripts/wt-land.sh`),
  from the main checkout only: refuses a dirty worktree and a branch whose
  base is not an ancestor of `origin/dev`; rebases onto `origin/dev`, pushes
  with `--force-with-lease`; `gh pr create --base dev --fill` if no PR, then
  `gh pr merge --squash --auto` (plain squash-merge as fallback), waits up to
  30 min; fast-forwards local `dev`; `wt remove`; deletes the local and remote
  branch. `--local` merges with `git merge --no-ff` in the main checkout, runs
  `make lint && make test` (`WT_SKIP_CHECKS=1` skips), pushes `dev`. It runs
  from the main checkout because `gh` cannot delete a branch a worktree still
  has checked out, and because that is the only checkout allowed to push `dev`.
- **`scripts/wt-teardown.sh`** (the `pre_remove` hook, safe to run twice):
  kill the session, `fuser -k` both ports (only when `.env.worktree` exists,
  otherwise the ports would default to the main checkout's and kill its
  servers), drop the branch database when one was cloned.

`wt list` / `wt status` show every worktree; `wt cleanup` removes those whose
branch is merged.

### 2.6 The database half (resslab-hub only)

Skip this section in a repo without PostgreSQL. In resslab-hub, one container
holds the 3.4 GB shared dev dataset (database `postgres`) plus two idle
templates. Every worktree gets a clone of the ~20 MB light template (under a
second), owned by its own Postgres role `wt_<slug>` with a random password
written only to that worktree's `secrets/.env`; `CONNECT` is revoked from
`PUBLIC` on every database the script manages, so a worktree cannot reach
another database whatever its `POSTGRES_DB` says. Migrations are ON for the
clone, OFF when the worktree had to stay on the shared DB. `pytest` uses a
per-worktree `POSTGRES_TEST_DB`, created from a `POSTGRES_MAINTENANCE_DB` the
role can connect to. Commands: `make db-template-light`, `db-template`,
`db-branch`, `db-branch-full`, `db-branch-drop`, `db-status`
(`scripts/wt-db.sh`). Full detail in the guide, section "Database".

## 3. What Claude may do in a worktree

The session runs in **auto mode** with the OS sandbox on (both set in
`~/.claude/settings.json`, which only the user can edit). On top, the generated
`.claude/settings.local.json` adds three layers:

| Layer | Content | Note |
| --- | --- | --- |
| `permissions.allow` | the repo's own test/lint commands, and read-only `curl` to `http://localhost:*` / `http://127.0.0.1:*` in the common forms (bare, `-s`, `-sS`, `-fsS`, `-i`, `-I`) | skips the classifier for "did my change work" |
| `permissions.ask` | write forms of `curl`/`wget`/`http`/`gh api`; `gh pr create/merge/review`, `gh issue create`, `gh release`, `gh repo`; running downloaded code (`sh`, `bash`, `bash <(...)`, `$(curl ...)`, `eval`, `npx -y`, `pnpm dlx`, `uvx`, `pipx run`, `pip install git+/http`, `chmod +x`); `dangerouslyDisableSandbox:true` | prompts **always**, even in auto mode; no allow rule can override an ask rule |
| `permissions.deny` | `git push` to `dev`/`stage`/`main` in every spelling, force push, `git remote set-url/add`, `claude *`, every mutating connector tool (Calendar, Drive, Notion writes, Figma) | never |
| `sandbox` | writes confined to the worktree (plus the data repo in `additionalDirectories`); network to github, pypi, npm, context7 without a check, other hosts judged per host; `docker *` and `curl *` excluded from the sandbox | the Linux sandbox cannot reach loopback, so `curl` must run outside it to see the worktree's own servers |

Two rules learnt the hard way:

- **Never put a bare interpreter in `ask`** (`python3 -`, `python -`,
  `node -`, `perl -`). Auto mode edits files through `python3 - <<'EOF'`
  heredocs; the rule matches the command prefix and prompted on every single
  edit (2026-09-04). Removed in resslab-hub commit `cb4d653`. The classifier
  still blocks `curl x | python3 -` on its own.
- **The template is read from the main checkout**, and a live worktree's
  `.claude/settings.local.json` is only refreshed by re-running
  `scripts/wt-setup.sh` there, by the user: the classifier refuses to let an
  agent rewrite a permission file, its own or another checkout's.

Outside Claude, and not negotiable by it: `scripts/git-push-guard.sh` in
git's `pre-push`. Inside a worktree it refuses any push whose target is not
the worktree's own branch and any push to a protected branch; the main
checkout is exempt. Machine-wide `push.default current` means a bare
`git push` cannot even name another branch. In resslab-hub the guard is a
lefthook job with `use_stdin: true`; without lefthook, install it as the
shared `pre-push` hook (bluecity-viz's `wt-setup.sh` step 6 does that and
chains a pre-existing hook such as git-lfs's).

`CLAUDE.md` states the same rules in prose. The classifier reads it too, so
the section steers both the agent and its reviewer. Not optional.

## 5. Machine-level pieces (once, already done on this machine)

```bash
go install github.com/timvw/wt@latest          # ~/go/bin/wt
wt init                                        # shell function so `wt create` cd's for you
git config --global push.default current       # done
git config --global push.autoSetupRemote true  # done
printf '**/.claude/worktrees/\n' >> ~/.config/git/ignore
printf 'bind s choose-tree -wZ -O name\n' >> ~/.tmux.conf   # done: sessions sorted, one expand shows the panes
scripts/claude-notify-install.sh               # done: ~/.local/bin/claude-notify + hooks in ~/.claude/settings.json
echo 'source ~/code/<repo>/scripts/wt-go.bash' >> ~/.bashrc   # ONE source line for every repo, see section 6
```

`~/.config/wt/config.toml` (global):

```toml
strategy = "custom"
pattern  = "{.repo.Main}/.claude/worktrees/{.branch}"   # where Claude Code puts its own worktrees
separator = "-"                                         # feat/foo -> feat-foo
```

`~/.claude/settings.json`, the parts that matter (the user edits it, never an
agent):

- `permissions.defaultMode: "auto"`; `sandbox.enabled: true`,
  `failIfUnavailable: true`, `autoAllowBashIfSandboxed: true`,
  `filesystem.allowWrite` for `~/.cache/uv` and `~/.local/share/pnpm` (the
  hard-link stores), `allowAllUnixSockets: true`.
- `permissions.ask` kept to `rm`, `git reset`, `git clean`, force push. A
  user-level ask rule prompts in every session and no project rule can
  override it.
- `autoMode.environment`: one block per repo (trusted repo and remote,
  protected branches, key internal services, related repos, CI/CD targets,
  routine commands). The resslab-hub block is the model; `/auto-mode-setup`
  drafts one. `autoMode.soft_deny` has the "never migrate the shared DB from a
  worktree" line.
- `hooks`: `Notification` (`permission_prompt`, `idle_prompt`) and `Stop` call
  `claude-notify`, which raises a desktop notification titled with the tmux
  session; a click flips the attached tmux client to that session, claude pane
  selected.

## 8. Smoke test (run from a terminal, not from an agent)

```bash
wt create test/smoke origin/dev            # hooks: setup, then a detached session
tmux ls                                    # "<repo>/test/smoke" exists
cd .claude/worktrees/test-smoke && cat .env.worktree
curl -sI "http://localhost:$FRONTEND_PORT/"        # 200
curl -sI "http://127.0.0.1:$BACKEND_PORT/docs"     # 200
git commit --allow-empty -m "test: smoke" && git push   # must work
git push origin HEAD:dev                                # must be REFUSED
git branch -vv                                           # upstream is origin/test/smoke, not origin/dev
wt remove test/smoke                       # teardown: session gone, ports free
tmux ls; lsof -i :$BACKEND_PORT
```

pre-push stdin and test nothing.

## 9. Traps, condensed

From the guide, the memory notes and the port. Each one cost a session.

- **`$WT_MAIN` lies**: it points at whichever worktree has the default branch
  checked out. Resolve the main checkout through `git-common-dir`. Never check
  out `dev` in a worktree.
- **A branch must not track its base** (section 2.2, step 0). Repair by hand:
  `git branch --set-upstream-to=origin/<branch>` or `--unset-upstream`; list
  the wrong ones with `git for-each-ref --format='%(refname:short) %(upstream:short)' refs/heads`.
- **A local ref makes a stale base**: pass `origin/<base>`, fetched first.
- **`post_checkout` may run on create too**: setup stays idempotent. Post
  hooks only warn on failure, read their output.
- **`ROOT` and the env keys leak into the tmux server** if the run that
  starts it has them exported; every later pane inherits them. `tmux-dev.sh`
  scrubs both.
- **The sandbox cannot reach loopback**: `curl` to the worktree's own servers
  returns `000` from inside it. `curl *` is excluded from the sandbox and
  governed by the classifier and the allow/ask rules instead.
- **The sandbox cannot reach the tmux socket**: an agent cannot start, attach
  or type into sessions. The user runs `wtgo`; the agent reads `.wt-logs/`.
  A brief written by an agent for another worktree is a block of `wtgo` lines
  for the user, one per line.
- **The sandbox cannot finish `wt-setup.sh`**: `.git/hooks` is read-only in
  it, so `lefthook install` (and a plain hook install) fails there. Worktree
  creation belongs in a terminal; a sandboxed re-run of setup is fine for the
  env file and the session-less parts.
- **An ask rule beats everything**: it prompts even in auto mode, and no allow
  rule at any scope overrides it. Keep `ask` to real write-to-the-internet
  forms and downloaded code. No bare interpreters.
- **`~/.claude/settings.json` and any `.claude/settings.local.json` cannot be
  edited by an agent**. Hand the user the text.
- **Start the database from the main checkout** (compose project name).
- **Never migrate a shared database from a worktree**; each worktree gets a
  clone or runs with migrations off.
- **Stale `node_modules` after a package-manager switch** breaks lefthook and
  commitlint in old worktrees (`Can't find lefthook in PATH`): `make install`
  there, `LEFTHOOK=0 git commit` meanwhile.
- **tmux session names** cannot contain `.` or `:`; `session_name()` maps them
  to `-`.
- **`wt-done.sh` must run the main checkout's copy of itself**, and hand the
  removal to the tmux server when run from the session it closes.
- **The `prefix+X` binding is server-wide**: the last `tmux-dev.sh` to run,
  from any repo, owns it. It must resolve `wt-done.sh` from the pane's
  checkout at key time, never bake a script path in (a bluecity session once
  left resslab worktrees calling bluecity's copy). The snippet is parsed by
  tmux before sh: backticks and single quotes only, no `$`, no double quotes.
- **Squash-merge lands a worktree branch** in `wt-land.sh`; a repo that keeps
  commit trailers on `main` needs single-commit PRs or a merge commit instead.
